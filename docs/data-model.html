Data model

Overview Architecture Extending Run & deploy

Persistence

Everything is stored in one localStorage key: kinetos.v1, as JSON. store.js owns it. migrate() deep-merges older data onto defaults, so adding new fields is backward-compatible. Bump the key/version only for breaking changes.

State shape

{
  version: 1,
  profile: {
    name, photo,            // photo is a resized data URL (jpeg, max 256px)
    sex: "male"|"female",
    birthdate,              // "YYYY-MM-DD"
    heightCm, weightKg,
    restingHR,             // optional, improves HR zones
    activityLevel          // sedentary|light|moderate|active|very
  },
  settings: { lang, theme, units },   // lang "" = auto-detect
  plans:    [ Plan ],
  sessions: [ Session ],
  customExercises: [ Exercise ],      // same schema as built-in
  tombstones: {                       // deletion registry — makes deletes propagate on sync
    plans:    { [id]: isoDeletedAt },
    sessions: { [id]: isoDeletedAt },
    templates:{ [id]: isoDeletedAt },
    customExercises: { [id]: isoDeletedAt }
  }
}

When an entity is deleted, its id + deletion time is recorded in tombstones. Sync unions tombstones (latest time wins) and drops any re-appearing id whose tombstone is newer than the entity's own last-modified time — so a delete on one device is not resurrected from another device's stale copy. Saving/re-adding an id clears its tombstone. Tombstones older than ~6 months are pruned.

Plan

{
  id, name, date,          // date "YYYY-MM-DD"
  notes,
  exercises: [ TargetRow ],
  source                   // optional; "ai" for plans created by the AI import in Profile
}

Target row (plans and templates)

A planned exercise comes in two shapes. Simple prescribes one set of numbers for the whole exercise; detailed ("Per-set" in the editor) prescribes each set on its own, which is what a ramp-up, a drop set, a rep ladder, intervals of different lengths or a one-off rest change need.

// simple — every set alike
{ exerciseId, targetSets, targetReps, targetWeightKg }

// detailed — one entry per set
{
  exerciseId,
  targetSets, targetReps, targetWeightKg,   // kept in sync, see below
  detailed: true,
  setTargets: [ {
    reps, weightKg,        // metric "reps"
    seconds,               // metric "time"
    distanceKm, minutes,   // metric "distance"
    count,                 // metric "count"
    restSeconds,           // rest AFTER this set; null = profile default
    note                   // short cue shown on that set ("drop set", "AMRAP")
  } ]
}

Only the fields matching the exercise's metric are present on a setTargets entry. In detailed mode setTargets is the source of truth: its length is the set count, and syncTargetRow() (js/workout.js) mirrors it back onto targetSets plus, for reps exercises, the heaviest set's targetReps/targetWeightKg. That mirror is what keeps every simple reader working — calendar and import-preview set counts, and a device still running an older build after a sync. Turning per-set mode off collapses the row back to those scalars and drops the rest overrides and cues.

When a session is created, reps/weightKg/seconds/distanceKm/count are prefilled onto the set (and also recorded as its target), restSeconds and note ride along, and a prescribed minutes becomes targetMinutes — a placeholder hint only, because the set runner fills an empty minutes with its measured time and a prefilled split would masquerade as a real one. A restSeconds override applies only while the profile's own rest timer is on; settings.restSeconds === 0 means no timer at all.

Model helpers, all in js/workout.js: isDetailedTarget, setTargetsOf, setTargetKeys, newSetTarget, syncTargetRow, toDetailedTarget, toSimpleTarget, cloneTargetRow, MAX_SET_TARGETS (20). entriesFromExerciseList() turns either shape into session sets; targetsFromSession() goes back the other way and produces a detailed row whenever the logged sets were not all alike.

Session

{
  id, planId|null, name,
  startedAt,               // ISO datetime
  endedAt|null,            // null => still active / in progress
  notes,
  entries: [ {
    id, exerciseId,
    sets: [ {
      n,                   // set number
      reps, weightKg,      // strength
      seconds,             // time-based (plank, jump rope)
      count,               // counted tally (metric "count", e.g. stair-stepper stairs)
      distanceKm, minutes, // cardio
      barKg,               // chosen bar weight (only when Profile → Barbell = "add bar")
      effort,              // 1=easy | 2=medium | 3=hard | null (RPE-style feedback)
      targetReps,          // planned/suggested reps — drives hit/miss autoregulation
      targetWeightKg,      // planned/suggested load
      targetMinutes,       // planned pace for a distance set (a hint, never a logged value)
      restSeconds,         // per-set rest override from the plan; null/0 = profile default
      note,                // per-set cue from the plan ("drop set", "AMRAP"); "" = none
      done,                // boolean
      timestamp,           // ISO when marked done (seconds precision; for timing analysis)
      startedAt,           // ISO when the set runner was opened (null if logged without it)
      durationMs           // measured set duration from the set runner's stopwatch
    } ]
  } ]
}

Exercise schema (js/data/exercises.json)

{
  id,                      // kebab-case, unique; also the SVG filename
  group,                   // one of muscles.json "groups"
  view: "front"|"back",    // which silhouette the SVG uses
  category,                // movement pattern (informational)
  equipment,               // barbell|dumbbell|cable|machine|bodyweight|cardio|band
  metric: "reps"|"time"|"distance"|"count",
  countUnit,               // metric "count" only: locales key under units.* (e.g. "stairs")
  primary:   [ muscleKey ],  // highlighted strongly in the SVG
  secondary: [ muscleKey ],  // highlighted lightly
  names: { en, de, fr, es, ru },
  cues:  { en: [ "step 1", "step 2" ] }   // how-to; add other langs as needed
}

js/data/muscles.json lists valid groups and muscles keys. Their display names live in each locales/*.json under groups.* and muscles.*.

Export / import

Profile → "Export data" downloads the whole state as kinetos-backup-YYYY-MM-DD.json. Import validates that the file is a Kinetos backup, then offers merge (adds templates/plans/sessions/custom exercises by id; local profile/settings win, the import only fills gaps) or replace (overwrites everything). The device-local sync provider choice is never taken from an imported file. Encourage regular exports — data is device-local only.

AI planning bridge (js/aiplan.js)

Profile → Your data has two buttons that let any external AI agent write plans, without the app ever making a network call.

"Generate AI prompt" opens a sheet with a mode toggle and the fields for that mode. buildPrompt() renders one always-English prompt; sections 2–8 are identical in both modes — the JSON schema and its rules, the profile + derived metrics, the weight-entry conventions (dumbbell single/pair, barbell included/added, bar weights, plates, rep presets, rest), today's date plus upcoming calendar plans, the allowed exercise catalog (non-hidden built-in + custom, with per-exercise weight steps and any athlete notes), set-level history and best estimated 1RMs. Only the framing (intro + section 1) and a few closing rules differ. The result is copied to the clipboard (with an execCommand fallback and a preview textarea for manual copy).

  • mode: "plan" (default) — "coach me". Section 1 is the athlete's request (default: plan tomorrow's session) and the agent designs the session, informed by the last maxSessions logged sessions (default 10, 0 = none).
  • mode: "describe" — "transcribe this". Section 1 is the workout(s) the athlete typed out themselves in free text, followed by strict transcription rules: keep every exercise in the written order, add nothing, change no stated number, map names (including synonyms and other languages) to catalog ids, skip anything with no match and name it in notes, fill only genuinely missing values and list those assumptions in notes, resolve relative dates ("tomorrow", "Friday") against section 5. The free-text box becomes optional extra instructions. History is a separate count (describeSessions, default 0) and, when shared, is labelled reference-only for guessing an unstated weight.

settings.aiPrompt remembers all of it: { mode, userMessage, extraMessage, description, maxSessions, describeSessions } — each mode keeps its own free-text box and its own history count, so switching modes never clobbers the other's settings.

"Import AI sessions" takes the agent's answer. parseSessions() strips markdown fences/prose, accepts the documented object as well as a bare array or single session, validates dates and every exerciseId against the catalog, coerces numeric strings, and reports fixable problems as warnings (missing sets → 3, missing reps → 12) or hard errors with the offending session/exercise/set index. The preview lists each date, name, exercise/set counts and whether that day already has plans; confirming calls importSessions() which saves one Plan per session (source: "ai") and jumps to the calendar.

Expected answer shape (schema version: 2; v1 payloads still import unchanged):

{
  "kinetos": "sessions",
  "version": 2,
  "sessions": [ {
    "date": "YYYY-MM-DD",
    "name": "Upper A",
    "notes": "",
    "exercises": [
      // (a) uniform work
      { "exerciseId": "bench-press", "sets": 4, "reps": 8, "weightKg": 62.5 },
      // (b) one object per set — a ramp, a drop set, per-set rest and cues
      { "exerciseId": "back-squat", "setTargets": [
          { "reps": 8, "weightKg": 60 },
          { "reps": 6, "weightKg": 70 },
          { "reps": 4, "weightKg": 80, "restSeconds": 180, "note": "top set" } ] },
      { "exerciseId": "plank", "setTargets": [ { "seconds": 45 }, { "seconds": 60 } ] }
    ]
  } ]
}

setTargets length is the set count (1–20) and wins over sets; an array handed over as sets is accepted too, since agents do that often enough. Each entry may only use the metric fields of its exercise (reps/weightKg, seconds, distanceKm/minutes, count) plus restSeconds and note; unusable numbers leave that field blank with a warning rather than failing the import, because the prescribed structure is the valuable part. With form (a) a time/distance/count exercise can still only say how many sets, so the prompt tells the agent to reach for setTargets there.
